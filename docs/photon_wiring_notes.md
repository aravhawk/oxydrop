### 1.2 Engine contract used by `app.js` (what a new engine must provide)

The app touches only these members of `chain`: `push(r, g, b)`, `n` (samples pushed), `ac[ch]` (band-passed log signals for the waveform, `slice(-300)`), `calibrationSummary()`, and optionally `info`, `latency()`, `close()`, `degrade()`, `degraded`, `oldestPendingMs()`, `worker`, `core` (replay note says the model was trained on the demo person when `chain.core` exists). `engine.js` `Chain` has `push`, `ac`, `lg`, `n`, `calibrationSummary` and no optional ones.

A window object (the "decision object") is returned by `push` when a new 2 s window completes (null otherwise) or is delivered through the `onWindow` callback of an async engine. Fields read by `app.js`, `decision.js` and the CSV/debug code: `s` (window start second), `calibrating`, `warm`, `valid`, `sqi`, `acf`, `ch`, `sat`, `hrEst`, `hrBeat`, `hr`, `dHR`, `p`, `label`, `z`, `c`, `corr`, `cnnHr`, `specHr`, `spo2Exp`, `state`, `n` (async engines: samples pushed when the window ended), `engine` (string id, written to the CSV), `cameraHrOverride` (added by `dispatchWindow`).

### 1.3 Per-frame data

`camera.js` (`CameraSource`) takes the mean R,G,B of a central ROI of each video frame (0..255, nominal sRGB-ish camera output after the locks), `resample.js` (`Resampler`, `rs`) puts it on a fixed 30 Hz grid, and `sink(r, g, b)` (app.js line 294) calls `record(r,g,b)` (raw ring buffer, 15 min) and `chain.push(r, g, b)`. Replay feeds `sink` from `app/data/replay/<rec>.bin` (Float32 R,G,B triples at 30 Hz, `.json` holds `n`, `person`, `weights` and the reference `spo2`). So every engine gets exactly three numbers per tick, at 30 Hz, no timestamps (the engines default `dt = 1/FS`; `HybridCore.push(r,g,b,dt,wantCnn)` takes a frame interval but `sink` does not pass one). Per-frame RGB is the only input; accelerometer, fps and gap context live in `liveCtx()` and enter only through `decide()`.

Streaming layout inside engines: `engine.js` `Chain` keeps `lg` (ln(max(x,1e-3)+1)) and `ac` (the 3-section Butterworth band-pass 0.7 to 4 Hz) per channel; a window completes every `STEP * FS = 60` samples once `n >= WIN * FS = 300` (10 s window, 2 s hop, FS 30). The first `CAL = 60` s are calibration (label-free baseline = median of the valid rows); decisions start at `s >= 60` (first answer at 70 s). Constants exported from `engine.js`: `FS, WIN, STEP, CAL, BAND, FUSION`.

## 2. How the three-state output is produced

1. The engine labels each window: `label` is one of `'normal'`, `'HYPOXIC'`, `'unsure'`, `'nolock'` (no pulse lock), `'low_ac'` (hybrid only: pulse weaker than anything trained on, `lacMax < OOD_LAC_MIN = -6.02`). In the hybrid, `finishWindow` maps the conformal state of the decision logit `z` (`NORMAL` if `z < normal_below`, `LOW` if `z > low_above`, else `UNSURE`, thresholds in `app/data/conformal.json` at default alpha 0.10) to `normal`, `HYPOXIC`, `unsure`. In the logistic chain it is `p = 0.5 (LR_hr + LR_fusion)`; `|p - 0.5| < BAND (0.10)` is `unsure`.
2. `decision.js` `decide(d, ctx)` is the only place that produces the user-facing state. `qualityReason(d, ctx)` returns the first failing gate in this order: camera stalled, calibration failed, no finger, moving (`> 0.35 m/s^2`), fps `< 20`, frame gaps (`>= 3` events in 10 s, a gap `> 1.0 s`, `> 3.0 s` missing in 30 s), saturation (`d.sat > 0.10`), `!d.valid`. If a gate fails, the state is `UNSURE` with that reason. Otherwise the label decides: `nolock` and `low_ac` and `unsure` give `UNSURE` (reasons `nolock`, `low_ac`, `model_unsure`), `HYPOXIC` gives `LOW`, `normal` gives `NORMAL`, any other label gives `UNSURE (invalid)`: "never guess".
3. `STATE_TEXT`: `NORMAL` = "Normal vs your baseline", `LOW` = "Possible low oxygen: re-check with a pulse oximeter", `UNSURE` = "Unsure, re-measure". `app.js` `onWindow(d)` calls `decide(d, liveCtx())`, overrides with an `UNSURE / weak_signal` state when the live signal-quality check fires, and renders status, tally and strip.
4. Consequence for a new engine: it must expose the same window fields and labels, set `valid`/`sat`/`hr` from the v2 quality chain (reuse `engine.js` `Chain` as `HybridEngine` does), and map its own abstention to `label: 'unsure'` (reason `model_unsure`) so `decide.js` and its test (`tests/decision.mjs`) stay unchanged. The answer of a model that abstains (OxyTrack band, PhotonTwin posterior width, FlashGap conformal `answer`) goes through `label`, never through a new state.

## 9. Pitfalls found during the read

* `check_claims.py` check (4) cannot see `results/photon/` (section 7). Without a change every photon number in MODEL.md fails with "3-decimal numbers not found".
* `tests/sw_assets.mjs` demands every file in `app/js/` be precached, so adding `photon_engine.js` without touching `sw.js` fails `npm test`.
* The build string in `app/js/app.js` line 166 duplicates `const V`; `docs/APP_INTEGRATION.md` line 66 and `results/ml/DEPLOY.md` line 29 also name an old cache version (historical, leave).
* `flow.mjs` greps the exact hybrid debug string; the fake `Worker` in it is installed only when `FLOW_ENGINE !== 'logistic'` and returns `{calibrating: true}` for every window, so any new async engine needs its own stub or must run in-thread.
* `app.js` falls back from the hybrid to the logistic chain, never to another engine. Keep that rule for the photon engine (a fallback to the CNN hybrid would silently change the model and its numbers).
* Replay (`kind === 'replay'`) uses the in-thread engine and `data/replay/100001L` and `100004R`: both people are in the training set of any all-people refit, so the replay note must stay "demo only, not a test" for the photon engine.
