# App integration: the hybrid model as the on-device main path

The app (`app/`) runs the final hybrid model in the browser with dependency-free JavaScript. The v1 logistic chain and the textbook ratio-of-ratios are baselines in the results tables, and the chain logit and the baseline-relative ratio channels are inputs of the model (a physics-informed hybrid). Research prototype, not a medical device.

## Data flow

```
camera frames -> Resampler (30 Hz R,G,B) -> v2 quality chain (engine.js, main thread)  -> valid / SQI / saturation / HR (spectral) / calibration summary
                                          \-> HybridCore (hybrid_engine.js; Web Worker in the live app)
                                                v1 physics chain (engine_v1.js, weights embedded in hybrid_weights.json)  -> c = logit(p_chain)
                                                CnnInput (cnn_features.js): 10 s x 10-channel tensor + 9 side features, first-minute baseline
                                                3 x OxyNet (cnn.js, hybrid_R_s{0,1,2}.json, 167,588 parameters each)       -> corr (mean lowox_logit), CNN HR (median of 3)
                                                r = c + corr -> meta-learner (hybrid_weights.json pipeline.meta)            -> z (z > 0: possible low oxygen)
                                                conformal rule (conformal.json, default alpha 0.10)                         -> NORMAL if z < -0.965, LOW if z > 0.389, else UNSURE
finishWindow(): window object with the fields decision.js decide() expects ({valid, sat, label, hr, ...}); the quality gates of decision.js stay in front.
```

* **Label.** `normal`, `HYPOXIC`, `unsure` from the conformal rule; `nolock` when the v2 pulse-lock gate fails. `decide()` and the three UI texts are unchanged.
* **Baseline.** The first 60 s are label-free calibration (same checks as before: finger coverage, frame rate, stalls, resting HR range). The baseline embedding of the low-oxygen head is the mean embedding of up to 8 evenly spaced calibration windows rebuilt with the finished baseline (`CnnInput.baselineWindows`, the training convention of `train.group_emb`).
* **Heart rate.** Rule `agree` (declared in Amendment 3): the mean of the CNN estimate and the v2 spectral estimate when they are within 5 bpm, otherwise the CNN estimate. It is shown only when the v2 gate says the window has a pulse lock. This rule is **post hoc and exploratory, not a clean win**: it was chosen after the pooled P2 table had been seen (Amendment 3). On Hoffman alone the spectral estimator is more accurate than this rule (0.883 against 0.826 within 5 bpm), on MTHS the spectral estimator is nominally better (0.633 against 0.594), and the pooled gain on the 100 BUT PPG and MTHS people (0.480 against 0.419) comes from BUT PPG (0.419 against 0.304). On the synthetic 72 bpm test video the CNN reads 4 to 5 bpm high, so the e2e tolerance is +-6 bpm.
* **SpO₂.** No SpO₂ number in the main UI. The CNN SpO₂ head only appears in the debug view on a line labelled `EXPERIMENTAL ... (not validated, do not use)`. Reason: on the OpenOximetry contact sensor the CNN ties the textbook ratio-of-ratios (SaO₂ MAE 2.94 against 3.07, `results/ml/OPENOX_SPO2.md`), and on MTHS (normoxic) it shows no skill over the training mean.
* **Low-amplitude guard (generic).** lac is the log of the standard deviation of the band-passed log-intensity of the 10 s window (about the AC/DC ratio of the pulse); the guard takes the largest of the three channels. If it is below -6.02 (an AC/DC ratio of 0.24 %), the 0.1th percentile over all windows of the six Hoffman people (`scripts/ood_range.py`, `results/ml/ood_ac_range.csv`), the window gets the label `low_ac`: the answer is *Unsure* with a reason text about a pulse weaker than the model was trained on, and the heart rate shown is the spectral estimate only. This is a range check on the training data, not a phone setting. It exists because the pulse-lock gate is scale free: a clean but very weak pulse (a flash far from the lens) would otherwise reach the network, which has never seen such a signal. On the fixture recordings it refuses no window of person 1 (his lowest window is -5.95), and a person 1 pulse attenuated to 3 % is refused in all 39 windows that still lock. Cost: a phone whose pulse is always weaker than 0.24 % AC/DC will always answer *Unsure*; that is a limitation, not a tuning target. **Refusal rate on other studies' phones** (`share_below_cut` in `results/ml/ood_ac_range.csv`, measured by `scripts/ood_range.py` with the cut that ships, `OOD_LAC_MIN` in `hybrid_engine.js`): 0.1 % of the Hoffman windows the cut was derived from, **6.7 % of MTHS windows and 8.8 % of BUT PPG windows**. A phone with a weak flash will therefore see more *Unsure* answers, and a refused window shows the spectral heart rate only (a path no P2 table evaluated). The rate on any untested phone is unmeasured.
* **Slow pulse (Hoffman person 4, 43 bpm).** The v2 gate cannot lock below about 51 bpm (spectral floor), so every window is `nolock` and the answer is *Unsure*. That is the existing gate, not the CNN: the CNN does not track this person either (MAE 21 bpm, `results/ml/HR_VOTE.md`).

## Files

| file | role |
|---|---|
| `app/js/hybrid_engine.js` | `HybridCore` (v1 chain + CNN + combiner + conformal), `HybridEngine` (v2 quality chain + core, one thread), `finishWindow`, `conformalState`, `hrAgree`, `loadHybridAssets` |
| `app/js/hybrid_async.js`, `app/js/hybrid_worker.js` | live path: the quality chain stays on the main thread, `HybridCore` runs in a module Web Worker so a CNN pass never delays camera frames; results arrive 50 to 300 ms after a window ends |
| `app/js/cnn.js`, `app/js/cnn_features.js` | forward pass and causal input tensor (parity-tested against PyTorch and numpy) |
| `app/data/hybrid_weights.json` | pipeline definition: embedded v1 chain weights, meta-learner, members, checkpoint hashes |
| `app/data/hybrid_R_s{0,1,2}.json` | the three CNN seeds (0.9 MB each, BatchNorm folded, phone input scale folded in) |
| `app/data/conformal.json` | Mondrian conformal thresholds per alpha (`oxydrop-conformal-v1`) |
| `app/data/oxynet.onnx` | ONNX export of seed 0 (interoperability only; the app does not load it) |
| `app/data/weights.json` | v2 logistic chain: quality gate and the `?engine=logistic` baseline |
| `results/ml/FINAL_MODEL.json` | weights hashes, parameters, seeds, training subjects (`scripts/final_model_json.py`) |
| `results/ml/DEPLOY.md` | latency per window and asset sizes |
| `results/ml/ood_ac_range.csv` | training range of the pulse amplitude behind the low-amplitude guard (`scripts/ood_range.py`) |

The embedded v1 chain differs slightly from `weights.json` (largest coefficient difference 0.58) because the meta-learner was fitted on that refit chain; the app uses the embedded weights for `c`.

## URL switches
* default: hybrid. `?engine=logistic`: the v2 logistic chain alone (the baseline of the comparison, also the fallback if the hybrid files cannot be loaded; the debug `engine` line says which one runs and why). **A failed hybrid load is not silent**: the measurement screen shows a one-line notice ("the neural-network part of the model could not be loaded, so these answers come from the simpler logistic chain alone. Reload the page to try again"), text only, no device logic; the three result words are unchanged. It is not shown when the chain was requested with `?engine=logistic`. **A worker that fails after loading is not silent either**: if the CNN Web Worker raises an error, or leaves a window unanswered for 2 s (a healthy worker answers in 50 to 300 ms), the page terminates it, the running measurement continues on the logistic chain (the quality chain inside the worker engine already holds the calibration, so nothing restarts), later measurements in the same page load use the logistic chain, and the screen shows a second one-line notice ("the neural-network part of the model stopped working, so from now on these answers come from the simpler logistic chain alone. Reload the page to try again"). The debug `engine` line records the error. At most two windows (including calibration) may be pending. Queued decisions are delivered from the calibrated logistic chain. The 2 s deadline runs on a per-window timer and the page's UI timer; the error path is tested end to end, the stall path at engine level (`tests/worker_fail.mjs`).
* `?alpha=0.05` sets another conformal level from `conformal.json` (debug only; `0.20` is past the crossing point and refused). The declared default is 0.10.
* `?rec=100001L|100004R` picks the replay recording.

## Replay demo: in-sample, demo only
The three CNN seeds, the embedded chain, the meta-learner and the conformal thresholds were all fitted with the six Hoffman people, including the two replay recordings (100001L and 100004R). Per-fold held-out weights exist only as prediction tables (`results/ml/scores/`), not as checkpoints, so the replay screen says **"Model trained on this person: demo only, not a test"** and so does the tally line. The honest held-out numbers are in `results/ml/HYBRID.md` and `CONFORMAL.md`. `?engine=logistic` replays with the v2 chain weights fitted without that person, as before.

## Device agnostic by construction
Nothing is fitted to a phone. Per-lens probing, adaptive exposure and the placement, motion, frame-gap, saturation, stall and calibration gates are generic. The three iPhones named in `docs/PHONE_CHECKLIST.md` are a held-out sanity check by the team; untested Androids and other phones are a limitation. Known cost: the model runs on the CPU of the phone. The latency per window is reported in the debug view and in `results/ml/DEPLOY.md` (laptop numbers; phones are slower and unmeasured).

## Tests
`npm test` runs, besides the earlier suites:
* `tests/cnn_parity.mjs`: JS forward pass against PyTorch on the shipped seed 0 (worst 4e-6), streaming features against numpy.
* `tests/hybrid_engine.mjs`: combiner against `tests/fixtures/hybrid_ref.json`, conformal rule against `conformal.json` examples, the streaming engine on the two Hoffman fixture recordings against `python/oxydrop_ml/make_engine_ref.py` (PyTorch checkpoints of the three exported seeds, v1 chain of `python/oxydrop`; chain logit 1e-12, CNN correction 2e-6, CNN HR 1e-5 bpm, z 2e-6), the quality gates in front, the HR rule, and the Web Worker path against the in-thread engine (identical).
* `tests/sw_assets.mjs`: every file the hybrid needs offline is in the service-worker precache and the cache version was bumped.
* `tests/flow.mjs`: the camera-flow regression tests of the review fixes, plus the default engine check. `npm run test:flow` runs it four times: default (hybrid, no notice), `FLOW_HYBRID_FAIL=1` (the hybrid assets answer HTTP 503: logistic fallback and a visible notice), `FLOW_WORKER_FAIL=1` (a stand-in Web Worker loads, then errors during the measurement: the logistic chain takes over and a visible notice appears; `tests/worker_fail.mjs` covers the unanswered-window stall and the degraded engine) and `FLOW_ENGINE=logistic` (the live camera path with `?engine=logistic`: logistic chain, no notice).
* `scripts/check_claims.py` (run by `npm test` through `scripts/check_claims.sh`): the generated documents equal a fresh render, every quoted number is recomputed from `results/ml/*.csv`, and the numbers typed into the app text (`app/index.html`) and `conformal.json` `nested_evaluation` match the CSVs.
* Browser e2e (`tests/e2e/fake_camera.mjs`, see `tests/e2e/README.md`): good, bad, replay, replaylog, stall, calstall.

Regenerate the engine reference after any model change: `python python/oxydrop_ml/make_engine_ref.py --ckpt-dir <runs>/hyb_final`, and `python python/oxydrop_ml/export_js.py --ckpt <runs>/hyb_final/R_s0.pt --onnx app/data/oxynet.onnx --fixture tests/fixtures/cnn_ref.json` for the single-network fixture (its JSON weights default to a temporary file; the shipped members are written by `export_hybrid.py`). Both fixtures carry the SHA-256 of the checkpoints they came from (`ckpt_sha256`), and `tests/hybrid_engine.mjs` and `tests/cnn_parity.mjs` compare them with the hashes in `hybrid_weights.json`.


Capture update (2026-11-15, cache `oxydrop-v3.3-capture`): enumerate every exposed rear device after permission; prefer usable physical cameras, probe each for 1.5 s after 0.5 s settling and rank 0.7–3.5 Hz AC/DC signal against residual noise. The ROI is selected from illuminated regions with an unclipped channel and held stable while measuring. Debug overlay (`?debug=1`, Capture debug toggle) reports actual camera label, torch readback/unknown state, ROI and full-frame RGB, channel clipping, FPS, SNR and gate reasons. The placement darkness floor now detects near-black digital values (max RGB <=3), rather than requiring red DC >=50. Placement still requires relative red dominance; pulse validity is independent. Torch and manual exposure/WB/focus are best effort where the browser exposes support.

Live capture uses an opt-in spectral/ACF harmonic check and beat-spacing guard; clipped channels are excluded from live HR selection. A disagreeing CNN HR cannot override the valid spectral/ACF/beat estimate. Published tables and replay retain the original research estimator and model weights: parity tests are unchanged; their accuracy percentages do not validate the new capture path. The new live behavior has synthetic regressions, and real-phone confirmation remains required. Low-AC oxygen refusal and all trained model thresholds remain unchanged. Live worker failure uses the logistic chain; heavy in-page inference is reserved for replay.
